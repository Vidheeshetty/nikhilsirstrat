1. High-Level Overview

The framework separates strategy logic from the execution infrastructure so that trading ideas can be iterated rapidly while backend engines (e.g., Nautilus-Trader) can be swapped in without breaking the public API exposed to data-science notebooks, CLI tools, or CI tests.

2. Core Components

2.1 Strategy Layer

Strategies inherit from utils.strategy.BaseStrategy. They receive quotes/bars via the on_quote/on_bar hooks and emit orders by interacting with the injected engine. In src/strategies/trend_riding/ the Trend-Riding example showcases:

  • TrendRidingConfig – holds user-tunable parameters (lookback, SL/TP, etc.).
  • entry.py & exit.py – pure-function helpers to decide entry/exit.
  • risk.py & position.py – size & risk calculations.

The strategy is entirely decoupled from how data is fetched or how the engine calls it — enabling quick unit testing with synthetic prices.

2.2 Runner Layer

Runners orchestrate data retrieval, engine lifecycle, and metric aggregation.

  • Single-Instrument Runner: TrendRidingBacktestRunner
     · Instantiates EngineManager & DataManager.
     · Wires strategy into the engine then executes run_backtest.
     · Returns a JSON-serialisable summary (PnL, Sharpe, etc.).
  • Batch Runner: TrendRidingBatchRunner
     · Delegates to generic utils.runners.BatchRunner for concurrency.
     · Aggregates individual summaries into portfolio-level metrics.
  • EngineManager: runtime adapter that chooses between the lightweight stub BacktestEngine or the full Nautilus-Trader implementation if present.

2.3 Utilities & Helpers

The utils/ package houses reusable building blocks:

  • data/ – DataManager plus adapters for CSV/Parquet ingestion.
  • runners/ – concurrency helpers (BatchRunner), metric functions, and base classes for live trading.
  • strategy/ – BaseStrategy + validation & indicator helpers.

3.2 Batch Aggregation

The BatchRunner spins up a ThreadPoolExecutor where each task executes the single-runner flow above. After completion it collates PnL, Sharpe, and drawdown statistics into a portfolio view.

4. Customisation & New Development Guide

  1. Create a New Strategy
    1. Fork src/strategies/trend_riding into src/strategies/your_strategy_name.
    2. Implement strategy.py, inheriting from BaseStrategy. Override on_quote/on_bar.
    3. Add unit tests under tests/strategies/your_strategy_name.
  2. Write a Single-Runner
    1. Subclass or replicate TrendRidingBacktestRunner.
    2. Replace references to TrendRidingStrategy with your own.
  3. Batch Execution
    1. Wrap the single-runner with utils.runners.BatchRunner (or create a thin adapter akin to TrendRidingBatchRunner).
    2. Expose a run(instruments: Iterable[str]) API returning aggregated metrics so that CLI & notebooks remain consistent.
  4. Plug in Real Data
    1. Point DataManager(catalog_path=...) to your parquet catalog.
    2. Implement extra loaders under utils/data_adapters/ as needed.
  5. Extend Metrics
    1. Add new functions in utils.runners.metrics.
    2. Import & use them inside EngineManager.get_results().
  6. Move to Live Trading
    1. Implement utils.runners.base_live_runner (currently a stub).
    2. Adapt strategy hooks to emit real orders via the Nautilus API.

Remember to update requirements.txt if you introduce external packages and to add new tests so that the CI pipeline captures regressions early.

5. Glossary

BacktestEngine
Minimal stub (or Nautilus engine) that replays market data against a strategy.
BatchRunner
Utility that executes multiple independent back-tests concurrently.
EngineManager
Adapter that hides which concrete engine implementation is in use.
DataManager
Provider of price series & instrument metadata.
